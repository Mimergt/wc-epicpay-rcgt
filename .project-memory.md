## 🏗️ Architecture & Design Decisions

### Payment Gateway Pattern
- **Pattern**: WC_Payment_Gateway singleton (EpicPay class)
- **Supports**: Both standard products and subscriptions
- **Authentication**: X-PUBLIC-KEY + X-SECRET-KEY headers (Recurrente API)
- **API Base**: https://app.recurrente.com/api
- **Endpoints Used**:
  - POST /api/checkouts - Create payment/subscription checkout
  - DELETE /api/products/{id} - Cleanup after payment

### Checkout Pattern
- **Single_Checkout class**: Handles one-time payments
- **Subscription_Checkout class**: Handles subscription initial payments
- **Both use**: Same /api/checkouts endpoint, different payload metadata
- **Payload Format**:
  ```
  {
    items: [{name, amount_in_cents, currency, quantity}],
    success_url: with ?wc-api=epicpay&status=1&order=ID,
    cancel_url: with ?wc-api=epicpay&status=0&order=ID,
    metadata: {order_id, order_number, subscription: true (for subs)}
  }
  ```

### Environment Management
- **Model**: Active environment determines which credentials used
- **Resolution**: apply_environment_credentials() checks environment setting
- **Fallback**: Legacy fields support backward compatibility
- **UI**: jQuery conditional visibility hides unused fields

### Webhook & Callback System
- **Primary**: Redirect callback (immediate, user-facing)
  - Endpoint: woocommerce_api_epicpay
  - Called when user returns from Recurrente payment page
  - Updates order status immediately
  - More reliable than webhook in sandbox
- **Secondary**: Webhook handler (async)
  - Endpoint: recurrente-response.php
  - Handles payment_intent.succeeded/failed, bank_transfer_intent.* events
  - Respects configured order_status setting
  - Records subscription renewal payments

### Subscriptions Model
- **Orchestration**: WooCommerce Subscriptions plugin (orders billing, scheduling)
- **Payment Processing**: EpicPay gateway (creates checkouts at Recurrente)
- **Renewal Flow**:
  1. WC Subscriptions schedules next payment
  2. On due date, fires `woocommerce_scheduled_subscription_payment_epicpay` hook
  3. EpicPay creates new checkout for renewal amount
  4. Customer completes payment
  5. Webhook records payment in WC order/subscription

## 🚀 Known Issues & Limitations

### Current Limitations
1. **Recurrente Subscription API**: Not publicly documented
   - Workaround: Using /api/checkouts for all payments (one-time + renewals)
   - Impact: No native subscription tracking at Recurrente (fine for WC management)
2. **Webhook Reliability**: Sandbox doesn't always fire webhooks reliably
   - Workaround: Redirect callback handles immediate status updates
   - Webhooks used for validation only

## 💡 Key Insights & Lessons Learned

1. **API Contract Discovery**: Recurrente API docs not always complete
   - Solution: Tested endpoints directly in sandbox
   - Key finding: /api/checkouts accepts metadata for custom tracking

2. **Redirect vs Webhook**: Redirect callbacks more reliable than webhooks in sandbox
   - Now using both for redundancy: redirect immediate, webhook validation

3. **WC Subscriptions Framework**: Powerful for managing billing logic
   - Leverages WC_Subscriptions_Manager, WC_Subscriptions_Order helpers
   - No custom renewal logic needed - WC handles scheduling

4. **Environment Switching**: Separate credentials per environment avoids test data in production
   - Design: Single gateway ID, multiple key pairs, runtime resolution

5. **Order Status Binding**: WooCommerce order status directly linked to subscription status
   - Be careful with payment_complete() - doesn't always force configured status
   - Solution: Check result and manually update if needed

6. **API Key Security**: Masking in UI important for admin UX
   - Implementation: jQuery mask + reveal-on-focus + preserve on submission

## 🔍 Code Patterns to Maintain

1. **Singleton Pattern**: EpicPay::get_instance() for gateway access
2. **Checkout Pattern**: Separate classes for different payment types (Single_Checkout, Subscription_Checkout)
3. **Metadata Storage**: Store references in order meta (epicpay_checkout_id, etc.)
4. **Environment Resolution**: Always call apply_environment_credentials() in constructor
5. **Error Handling**: Return WP_Error objects, check with is_wp_error()
6. **Webhook Routing**: parse_request_json() → handle_event() → specific handler method
